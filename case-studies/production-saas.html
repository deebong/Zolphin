Production SaaS Platform on Azure

Secure, scalable and operationally manageable Azure infrastructure for a production SaaS workload.

Reference architecture illustrating the ZOLPHIN approach to production Azure infrastructure. This is not presented as a client engagement.

The challenge

A SaaS application needs a production-ready Azure environment capable of supporting application workloads while addressing secure internet ingress, application and database isolation, secrets management, identity and access control, repeatable infrastructure deployment, CI/CD, monitoring, high availability and disaster recovery.

The architecture should provide a strong production foundation without introducing unnecessary Azure services or operational complexity.

Architectural decisions

Decision 01: Regional ingress

For a regional application, Application Gateway with WAF provides Layer 7 routing, web application firewall capabilities and private backend integration.

Front Door can be introduced when global entry, multi-region routing, edge acceleration or global failover is required.

For a global multi-region architecture, Front Door can provide the global entry point while Application Gateway handles regional ingress.

Decision 02: Application platform

App Service is appropriate for standard web/API workloads with minimal operational overhead.

Container Apps can be used for containerized workloads that do not require full Kubernetes control.

AKS is appropriate for complex microservices, Kubernetes-native requirements, advanced networking and orchestration.

VMs remain appropriate when OS-level control, legacy software or workloads that cannot be modernized require them.

Do not choose AKS simply because it is more advanced.

Decision 03: Private database connectivity

Prefer Azure SQL Private Endpoint for production workloads where private connectivity is appropriate. The application resolves the SQL FQDN through Private DNS and communicates over the Azure/private network.

Decision 04: Identity and secrets

Use Azure Key Vault for secrets and Managed Identity wherever possible. Applications should not embed credentials in source code, pipelines or configuration files.

Use Microsoft Entra ID and RBAC following least-privilege principles.

Decision 05: Infrastructure as Code

Terraform is utilized to provision and manage the entire environment, including:

  • VNets/subnets
  • NSGs
  • route tables
  • application platforms
  • Key Vault
  • Azure SQL
  • private endpoints
  • monitoring
  • supporting resources

Reusable modules and workspace configurations ensure environment separation across Dev, Stage/UAT, and Production.

Decision 06: CI/CD

Azure DevOps acts as the orchestrator for infrastructure state and application delivery. The pipeline strictly enforces the deployment process:

Code → PR → Validate → Terraform Plan → Review / Approval → Apply → Post-deployment Validation

Decision 07: Observability

The environment relies on Azure Monitor, Log Analytics, Application Insights, Diagnostic Settings, Alerts, and Dashboards.

Monitoring covers application health, infrastructure metrics, logs, failures, availability and important security/operational events.

Design for failure

Production deployments should not rely on a single application instance.

App Service

Multiple instances and health checks automatically handle failed nodes.

AKS

Native failed pod rescheduling and self-healing orchestration.

Container Apps

Automatic unhealthy replica replacement.

Application Gateway

Stops routing traffic to unhealthy backends based on probes.

Disaster recovery is an architecture decision

Regional disaster recovery planning relies on establishing the target RTO (Recovery Time Objective) and RPO (Recovery Point Objective).

Depending on critical services, acceptable downtime, and data loss limits, regional disaster recovery depends on:

  • database replication/failover
  • storage redundancy
  • secondary-region infrastructure
  • DNS/traffic cutover
  • private networking
  • Key Vault/secrets dependencies
  • runbooks
  • regular DR testing
Terraform can help recreate infrastructure consistently in the recovery region.

Engineering restraint matters

Not every production workload needs every Azure service. Unnecessary complexity introduces operational risk.

  • AKS when App Service or Container Apps is sufficient
  • Azure Firewall without a justified security/network requirement
  • Front Door for a single regional application
  • multi-region active-active without an RTO/RPO justification
  • excessive subnetting
  • multiple gateways/load balancers without a traffic requirement
  • complex Terraform module structures for small deployments
The architecture should solve the requirement—not maximize the number of Azure services.

Designed to evolve

If workload demand increases significantly, the first step is not simply increasing every resource.

Areas requiring reassessment before aggressive scaling include compute scaling, application platform, database sizing, read/write patterns, caching, asynchronous processing, network capacity, load balancing, monitoring thresholds, HA architecture, DR capacity, Terraform/deployment scalability, and cost.

Identify the actual bottleneck before changing the architecture.
